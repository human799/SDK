# 独立控制连接与安全（第一期落地）

## 1. 文档定位

本文约定终端 SDK 与转发节点之间 **「单独一条控制连接」** 的技术与安全要求——与业务转发 **逻辑分离**：**不走** `relayObfs` 透明 pipe，**不进入** upstream `f.target`。

- **端口策略（已定稿）**：控制与 Relay **共用同一 TCP 监听端口**（与既有 `-listen` 一致），**不**再单独开第二监听端口。分流在 **每条独立 TLS 连接** 上完成（推荐 **TLS ALPN**，见 §3.1）。  
- **实现代码**：可在后续迭代再合入仓库；**本文优先于代码**，作为联调与审计依据。

---

## 2. 架构摘要

```
                    同一 listen（同一 host:port）
┌─────────────┐  TLS + ALPN=控制   ┌──────────────────────────────┐
│ SDK 控制客户端│ ◄──────────────► │ Forwarder：按 ALPN 走控制协议 │
└─────────────┘                   │ （HELLO / PUSH，不进 upstream）│
                                  └──────────────────────────────┘
┌─────────────┐  TLS + ALPN=Relay  ┌──────────────────────────────┐
│ SDK 转发池   │ ◄──────────────► │ Forwarder.Handle → obfs → up   │
└─────────────┘                   └──────────────────────────────┘
```

| 通道 | 端口 | 用途 |
|------|------|------|
| **Relay** | **与 Control 相同**，单一 `-listen` | SOCKS/透明字节经 obfs → upstream，**不变**。 |
| **Control** | **同上**（**独立第二条 TCP/TLS 连接**） | 仅 **HELLO / 下行 PUSH**，载荷 **不进 upstream**；与 Relay **分流靠 ALPN（§3.1）**。 |

---

## 3. 传输与帧格式（草案）

### 3.1 传输层

- **TCP + TLS 1.2+**，与 Relay **共用监听地址与证书**（同一 `listen`、同一 `cert/key`）。  
- **同端口、不同 ALPN（推荐定稿）**  
  - **控制连接**：客户端在 TLS 握手中协商 **`cursor-control-v1`**（名称可在实现前最终锁定，全链路一致即可）。  
  - **Relay 连接**：协商 **既有 obfs 所用 ALPN**（或历史默认行为）；服务端按协商结果将连接交给 **控制处理器** 或 **obfs/Relay 处理器**。  
  - **禁止**在同一条 TLS 连接上混写控制 JSON 与 obfs 帧；控制必须是 **独立 TLS 会话**（可与 Relay **并行两条 TCP** 到同一 `host:port`）。  
- **不复用 obfs 承载控制**：控制通道在 **应用数据层** 直接承载 JSON/定长帧（见 §3.2～§3.3）；Relay 仍走 obfs 抗识别。

### 3.2 连接建立后第一条消息（客户端 → 服务端）

**HELLO**（建议单行 JSON + `\n`，便于调试）字段示例：

| 字段 | 说明 |
|------|------|
| `v` | 协议版本，当前取 `1`。 |
| `type` | 固定 `"hello"`。 |
| `device_id` | 与 SDK 持久化 **device UUID** 一致。 |
| `ts` | Unix 秒级时间戳。 |
| `nonce` | 随机十六进制串，防重放。 |
| `mac` | **HMAC-SHA256(PSK, 规范化拼接串)** 的十六进制输出，见 §4。 |

服务端校验通过后回复 **HELLO_ACK**（单行 JSON），例如：

```json
{"v":1,"type":"hello_ack","ctrl_interval_sec":60}
```

`ctrl_interval_sec` 建议下发客户端 **最小轮询/期望推送间隔**（可与《客户端发现与静默切换逻辑》中「每分钟」对齐）。

### 3.3 下行推送（服务端 → 客户端）

采用 **长度前缀 + JSON**（与二进制 MUX 帧区分，便于首期实现）：

1. **4 字节大端无符号整数** `payload_len`，`payload_len ≤ 256KiB`。  
2. **UTF-8 JSON**， envelope 建议包含：

| 字段 | 说明 |
|------|------|
| `v` | `1` |
| `type` | `"push"` |
| `ts` | 服务端时间戳。 |
| `nonce` | 单次推送唯一。 |
| `body` | **Raw JSON**：如 `config_version`、按设备的 **`endpoints` A～E**（见统一管控设计）。 |
| `mac` | 对 **`push|ts|nonce|` + `body` 原始 UTF-8 字节** 做 HMAC-SHA256(PSK) 的十六进制（与服务端签名算法一致即可）。 |

客户端 **校验 MAC 失败则丢弃本条**，**不得**更新路由表。

### 3.4 推送节奏

- **首次**：HELLO_ACK 后可立即 **可选首包 PUSH**（压缩冷启动延迟）。  
- **周期**：默认 **60s** 一条 PUSH（与产品文档一致）；具体以服务端策略为准。

## 4. 安全机制

### 4.1 PSK 来源与分发

- **Secret 载荷**增加可选字段 **`control_psk`**（与现有 JSON Token 一并签发或运维注入）。  
- **转发节点**通过环境变量或配置文件持有 **同值 PSK**（仅进程可读权限）。  
- **禁止**把 PSK 写进客户端日志；调试日志仅打印「校验失败」原因码。

### 4.2 HELLO 鉴权（MAC）

推荐拼接串（UTF-8）：

```
v1|hello|<device_id>|<ts>|<nonce>
```

`mac = hex(HMAC-SHA256(PSK, 拼接串))`。

服务端校验：

- MAC 正确；  
- `|now - ts| ≤ 120s`（可配置），防止简单重放。

### 4.3 PUSH 完整性（MAC）

推荐：

```
plain = "push|" + strconv.FormatInt(ts,10) + "|" + nonce + "|" + string(bodyJSONBytes)
mac = hex(HMAC-SHA256(PSK, plain))
```

其中 **`bodyJSONBytes`** 为 **`body` 对象的 JSON 序列化结果**（服务端签名与客户端验签必须使用 **同一字节序列**）。

### 4.4 TLS 与证书

- **首期**可与现有 Relay **相同自签证书 + 客户端跳过校验**（与连接池行为一致），便于快速打通。  
- **生产建议**：内嵌 **证书指纹 pinning**，或改用 **正规 CA + 域名匹配**，并在文档中单独立项验收。

### 4.5 限流与容量

- 每连接 **HELLO** 仅允许一次；后续仅服务端推送或扩展 **CTRL_REQ**（二期）。  
- 对 **ALPN=控制** 的连接单独做 **连接数/速率限制**，避免压垮与 Relay **共用监听** 下同进程的转发线程。

## 5. Forwarder 部署约定（占位）

| 配置项（示例名） | 含义 |
|------------------|------|
| `listen` | **唯一**对外监听（控制与 Relay **共用**，不再单独 `control_listen`）。 |
| `enable_control`（或等价开关） | **开启**后，对协商到 **控制 ALPN** 的连接走 HELLO/PUSH；关闭则 **拒绝**该 ALPN 或等同关闭控制面。 |
| `control_psk` | 与客户端 Secret 中 `control_psk` **一致**。 |
| TLS / ALPN | `cert`/`key` 一套即可；服务端注册的 **控制 ALPN** 与客户端 **必须一致**。 |

**推送内容来源（选一或组合）**：本地 JSON 文件、环境变量、或 **管控 HTTP 拉取** 后缓存签名下发（见《统一管控台系统设计》）。

---

## 6. SDK / Bootstrap 行为约定（占位）

- **Secret 含 `control_psk`** 且启用控制通道：在 **转发 ProxyClient `Start` 成功之后**，向 **与 Relay 相同的 `ServerHost` + 端口** 再建 **第二条 TLS 连接**，握手指定 **控制 ALPN**，跑 HELLO/PUSH；与 **Prepare** 使用的 OSS/域名 **并行存在**。  
- **`Stop`**：取消上下文，关闭控制连接，**不影响** Relay Stop 的语义。  
- **可选回调**：`SetControlPushHandler`（名称供参考）——应用层收到 **已验签** 的 `body` 后更新内存路由或与 `SDKBootstrap` 联动。

## 7. 测试验收（文档层）

| 编号 | 说明 |
|------|------|
| DC-01 | 仅 Relay ALPN、关闭控制（或未协商控制 ALPN）：行为与现网完全一致。 |
| DC-02 | HELLO MAC 错误 → 服务端关闭连接，无 PUSH。 |
| DC-03 | PUSH MAC 错误 → 客户端丢弃，路由不变。 |
| DC-04 | 篡改 `ts` 超出窗口 → HELLO 拒绝。 |
| DC-05 | Relay 高负载时刷 Control，Relay **吞吐下降在约定阈值内**（需压测标准）。 |

详细用例并入《统一管控台测试方案.md》时可引用 **DC-xx**。
